Architecture

One agent, run by the server on your computer

The window is only a renderer. When you send a message, the app server on your computer runs the agent: it builds the history, calls the model you linked with the tool definitions, runs each requested tool here, feeds the results back and repeats until the job is done. Anything that writes, deletes, installs or schedules stops at an Allow and Deny card first. The same agent serves the app, the Chrome extension’s side panel and MCP clients, so there is one agent, one memory and one set of approvals, however you reach it.

Rendering

One grammar draws every block

Rather than a separate page per kind of answer, Zod has one grammar, written in text, that draws every block: tables, charts, figures, lists, forms, cards and whole pages. The same grammar renders pages, chat answers, MCP tool results and the search box, so a connector’s app can look like Zod without shipping any design. Plain text passes through untouched, and a block that cannot be drawn says why instead of failing quietly.

Search

Filters that search and act

The search bar is also a small language. in: picks a place, is:, kind:, after: and sort: narrow it, free words match like grep with a typo allowed, and | do: acts on what was found. The same filters are the steps of a routine and the agent’s own way to find things, so what you can type, a routine can run and the agent can use. A step that changes something is tested with a dry run first.

Durability

Runs that survive a stop

Routines are stored as a schedule that may run a set of steps, and every run is recorded as it happens, on the server, so a chat or a run is still there after a restart. A run cut off by a stop is reported as cut off and is not repeated, so a routine never does the same thing twice by accident. Each run keeps its result and notifies you when it finishes or fails.
